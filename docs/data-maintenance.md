## 每周维护步骤

1. 查看现有 `Reviewable fuel data refresh` 工作流。OSM计划为周一00:00 UTC，参考价为周三06:00／10:00／14:00和周四06:00 UTC；GitHub调度可能延后。它仅有只读仓库权限，不提交或部署。
2. 成功时下载完整候选与构建来源记录；成功或来源失败时均下载诊断及质量前后报告、差异报告。两类附件保存14天，应在期限内审核和保存必要的脱敏证据。无需为查看状态重复触发下载。
3. 失败先看 `stage`、精确来源URL、错误及 `retainedPreviousPointers`，比较manifest和registry前后哈希。HTTP403保持失败；不能猜日期网址、绕过限制、换未许可来源或用地区参考价充当单站价。
4. 候选先在现有隔离工作区核对来源许可、实际输入校验和／时间、计数变化、所有引用与旧ID。使用 `npm run data:quality -- --output /tmp/after.json --compare /tmp/before.json --changes-output /tmp/changes.json` 对照字段缺口和变化；`UNCHANGED`不是HTTP刷新成功，运行 `npm run test:data` 和 `npm run check`。租车库另按 [契约说明](rental-data.md)保持身份映射、去重理由、来源、输入锁和全部下载项。
5. 差异合理且检查通过后，沿用Conventional Commit、main及开发分支快进推送和现有Cloudflare Pages生产部署流程。正式域名必须实际匹配引用数据哈希与日期；失败不替换现有快照。候选成功、GitHub推送和生产发布是三个不同状态。
6. 更新中文报告、当前TASKS与当前说明。保留原报告日期／历史结果；不要把后台等待状态改为PASS。无运行资源变化的文档补充不重复部署同一应用。

当候选明显超过已有计数变化阈值、来源身份／许可不清、旧ID冲突、日期倒退或解析失败时，调查后再决定；不得自动放宽阈值。用户手动下载官方工作簿时，也必须保留实际来源网址、字节数、哈希、调查及公布日期，才能走现有离线导入。

## 官方设施与字段缺口

每次计划维护先看 [缺口基线](data-quality.md)，优先处理已有真实反馈和17站样本中身份待核的对象，再复查8家三地区机场设施。门店资料与公司加油规则的核对日期分别显示，不把门店资料复核提升为规则复核。已核对日期满90天需复查；近期出行还应核对官方季节时段、休业例外和预约内容。官网设施位置不等于车辆入口，实际车辆入口仍需有直接证据。

官方地址、电话、提前返店时间与地图位置应分别核对。Times、Nippon、Toyota规则分别处理；仅使用已批准范围的有限事实，不复制官网图片／整页正文或宣称整库授权。没有依据的站点油种、支付和实时营业保持未知。
